ThinkVision Control: mockups

1 Main window 2 Experimental 3 Built-in 4 Tray 5 States 6 Narrow Open questions

Low-to-mid fidelity. Tokens, type sizes, 20 px gutter, 52 px slider rows and 6 px radii come from crates/tvc-app/ui/theme.slint and controls.slint. The window mocks are interactive: drag sliders, switch modes, tick displays, and press the inputs. Display names stand in for strings read from the device or the OS (EDID monitor name, DDC/CI capability string, DRM connector); the app never hard-codes a model name.

1. Main window, three displays

One window, one mode switch. "One at a time" edits a single display. "All together" turns the sliders into master sliders that move every linked display and keep the gaps between them.

Why it looks like this

  • The mode switch sits above the display picker, so it's clear which part the picker belongs to. The switch is hidden when only one display is connected.
  • Display chips show the device name and how it's connected. The selected chip uses the accent and aria-pressed. Experimental and built-in displays say so in the chip's second line, so nobody has to open each one to find out.
  • All together starts with which displays are linked, then shows one master slider per control. Each linked display sits under the master with its offset and the value it will get. Linking a display keeps its current value, and the difference becomes its offset.
  • Controls a display doesn't have stay in the list in grey, with a reason ("No volume control reported"). Nothing disappears without an explanation.
  • At 0 or 100 a display is clamped, and its row says "max" or "min". The offset is kept, so the gap comes back once the master moves away from the limit.
  • Changing a linked display in One at a time updates its offset, so the two modes always agree.

2. A display with no verified profile

The same window, with DELL U2720Q selected. It answers DDC/CI, but no profile matches it, so it gets only the standard MCCS controls.

Why it looks like this

  • "Experimental" appears twice: as a badge next to the name, and in one warning bar that says what it means in plain words. The Monitor tab is hidden because there's no profile to fill it.
  • Inputs are named from the MCCS codes in the capability string. When a code has no standard name, the tile says "Code 1B". The app doesn't guess a port name.
  • Switching input asks for confirmation inline, inside the page, with Cancel focused first. Escape cancels. Press "DisplayPort 1" to see it. The real dialog overlay isn't used, so the context stays visible.
  • Read-only row: the colour preset can be read but writing it isn't trusted, so the row shows the value with a lock and "Read only on this display" instead of a disabled dropdown.
  • "Copy capability report" is the one way to help support the display. It only copies to the clipboard, and the result appears inline. If the clipboard is blocked, the text is shown in a box so it can be selected by hand.

3. The built-in laptop panel

The same window, with "Built-in display" selected. Its brightness goes through the OS backlight (WMI on Windows, /sys/class/backlight on Linux), not DDC/CI.

Why it looks like this

  • The name is the OS's own, "Built-in display", because laptop panels rarely carry a useful EDID name. The header uses a laptop glyph and a neutral "Built-in" badge.
  • One info bar explains why there's so little: the panel isn't controlled over DDC/CI. This heads off "why is contrast missing?" reports.
  • Only brightness is shown. There's no Input or Colour section, and the Day and Night area is replaced by one plain sentence instead of disabled tiles.
  • The Monitor tab is hidden. Settings stays, because the app's own settings still apply.

4. Tray flyout

Opened by a left click on the tray icon. Quick brightness for every display without opening the window.

ENG14:32

Why it looks like this

  • Brightness only. It's the control people reach for many times a day. Everything else is one click away through "Open".
  • Each display gets a short card: its name and value on top, the slider below. The slider stays full width even when the name is long.
  • "Together" collapses the list into one master slider. It uses the same linked set and offsets as All together in the window. The displays stay listed underneath as read-only values, so it's still clear what moved.
  • The footer shows the next Day/Night switch, so the automatic schedule isn't a surprise.

5. States board

Every state with its exact wording. Each one names what it saw and suggests one next step.

Dotted underline marks a string read from the device or the OS (EDID monitor name, DDC/CI model, DRM connector, device node). The app fills these in at run time; none of them is typed into the app.

6. Narrow window, about 360 px

The same component with container queries. Drag the width to watch it reflow.

360 px

Why it looks like this

  • Display chips scroll sideways, snapping one at a time, with a peek of the next chip so it's clear there are more. They don't shrink until names become unreadable.
  • Slider rows wrap: the icon, label and value stay on the first line and the slider takes the full width below, so the drag target stays long.
  • Input tiles drop to two per row. Offset rows stack the display name above the stepper.
  • The gutter shrinks from 20 to 16 px and the header glyph gets smaller. Hierarchy and order don't change, so nothing moves to a different place.
  • The app today sets compact below 520 px and min-width 440 px. This layout needs that minimum lowered to 360 px.

Open questions

  1. Built-in display and the schedule. It has no colour presets. Should Day and Night still change its brightness, or leave it alone? The mock leaves it alone.
  2. One offset or one per control? The mock keeps a separate offset for each control on each display (brightness, contrast, volume). One shared offset is simpler, but wrong for panels with different ranges.
  3. Clamp or compress at the limits? The mock clips at 0 and 100 and keeps the offset. Compressing would keep the order of the displays but change the gaps.
  4. Is Experimental on by default? If it is, "No supported display found" only appears when even the standard probe fails. If it's opt-in, that state needs the "Try standard controls" button shown in the mock.
  5. Confirm input switches on verified displays too? The mock confirms only on Experimental. A verified profile could also confirm when the monitor reports no signal on the target port, if it reports that at all.
  6. Two displays with the same name (two P32p-20). Add the connector ("P32p-20 · DP-2"), the serial from EDID, or the position ("Left")?
  7. Chip order: follow the OS arrangement left to right (the mock's assumption), or put external displays first?
  8. Tray "Together": should it share the window's linked set, as the mock assumes, or always mean every display?
  9. Offset step: steps of 5 are easy to use with a keyboard, but too coarse for some. Should the stepper accept typing, or step by 1 while Shift is held?
