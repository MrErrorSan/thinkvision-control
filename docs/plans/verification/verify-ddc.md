# Verification: tvc-ddc claims in docs/plans/2026-11-14-audit-core-ddc.md (sections A and B)

Checked against branch feat/device-sourced-status (HEAD 3913f5a, working tree clean in crates/). I read every file in crates/tvc-ddc/src, plus tvc-core link.rs and engine.rs where they bear on the claims. Nothing was built or run. Paths are relative to `crates/tvc-ddc/src/` unless marked otherwise.

**Line numbers in the audit are often wrong.** Several citations point past the end of the file: packet.rs:236-260 (the file has 190 lines), macos/link.rs:356-375 and :415 (232 lines), macos/locator.rs:476-488 (113 lines). i2c.rs:252 and i2c.rs:146-200 point at unrelated code. The claims themselves mostly hold. The correct lines are given below.

Spec and ddcutil sources:
- VESA DDC/CI 1.1 (from memory): the null message is `6E 80 BE`, since 0x50^0x6E^0x80 = 0xBE. The host waits 40 ms before reading a Get VCP reply and 50 ms after a Set VCP or a capabilities request. A fragment with zero data length ends the capability string.
- ddcutil `ddc_packet_io.c`: `ddcrc_null_response_max = 3`. After that it returns `DDCRC_ALL_RESPONSES_NULL`, or `DDCRC_DETERMINED_UNSUPPORTED` when the monitor is known to use null for "unsupported" (not for capabilities).
- ddcutil `ddc_multi_part_io.c`: the accumulator starts at 2048 bytes and grows. There is no fixed cap. Only a zero-length fragment ends the string; a null reply does not.

## New issues

**N1. Linux `displays()` returns `Some([])` rather than `None` when nothing can be listed.** i2c.rs:136. Without KMS connectors (nvidia proprietary without `nvidia-drm.modeset=1`, or a headless box), `/sys/class/drm` still exists because it holds `version` and possibly bare `cardN`. The function then reports "no displays attached", which contradicts the trait contract: None means "can't list". On nvidia with KMS, the `edid` sysfs file can be empty, so you get `edid_id=""`, `name=""` and "an unnamed display". **Medium-Low.** Fix: return `None` when no `card*-*` connector dirs were seen.

**N2. macOS has the same null-message gap as Linux, plus a checksum side effect.** macos/link.rs:121-128 and mod.rs:96-98. If the connect-verify read of 0x10 gets null replies, the outcome is `InvalidReply`, and `fallback_checksum_mode` then retries in the legacy checksum form. A busy monitor is mistaken for a checksum-form problem. The bad form isn't stored (only `Ok` stores it), but it doubles the time. **Low-Medium.** Fix: handle null as in V1 before the fallback.

**N3. The macOS double write breaks DDC/CI timing.** mod.rs:19 and link.rs:135-136. The two copies are 10 ms apart, under the 50 ms the spec requires after a message. This is covered under V2, but it is a separate spec point. **Low-Medium.**

**N4. Windows `connect()` and `displays()` enumerate differently.** `connect` uses EnumDisplayMonitors + EnumDisplayDevices + dxva2 (dxva2.rs:70-81); `displays()` uses QueryDisplayConfig (dxva2.rs:251-290). A monitor that `displays()` flags `target=true` may never be found by `connect` (the V4 order or ACTIVE problem), and the user is told it is "there, but couldn't be opened" with no hint why. A description-hint match in `connect` is also never reflected in `target`. **Low.** Fix: build both from one source (DisplayConfig target ↔ `viewGdiDeviceName` ↔ HMONITOR).

**N5. Windows `display_kind` counts non-DDC transports as External.** dxva2.rs:300-311: `INDIRECT_WIRED` (DisplayLink USB), `MIRACAST` and `INDIRECT_VIRTUAL`-like wireless targets are External, though dxva2 DDC never works on them. They are then reported as a matching display that couldn't be opened. **Low.** Fix: map `INDIRECT_WIRED` and `MIRACAST` to a kind with no DDC, or note in the label that DDC is unavailable.

**N6. Windows `display_kind` OTHER rule.** `OTHER` with no EDID id becomes Virtual, which is right for RDP and IddCx. But an `OTHER` target that has an EDID id falls through to External, and some docks report `OTHER`. That is acceptable. No change needed; recorded as verified.

**N7. `edid_id_from_path` accepts any 7-byte ASCII second segment.** dxva2.rs:293-296. It doesn't check `[A-Z]{3}[0-9A-F]{4}`, so `"Default"` (from `Default_Monitor` it is 15 chars and rejected, but other 7-character placeholders pass) can come through as an id. **Low.** Fix: validate the shape.

**N8. `edid::display_name` reads only the base block and the first 0xFC descriptor.** edid.rs:41-54. It doesn't check descriptor byte 4 == 0 and ignores names in a DisplayID or CTA extension. Fine for nearly all monitors. Non-printables become '?', which is good. **Low.**

**N9. `edid::id` and `edid::matches` don't verify the EDID checksum.** edid.rs:8-13, 32-37. A corrupted I²C EDID read (i2c.rs:375-382 has no retry) is just a non-match, so the cost is a spurious `NotFound` on a noisy bus. The sysfs EDID is already validated by the kernel. **Low.** Fix: verify the byte-127 checksum and retry once in `read_edid`.

**N10. Linux `displays()` sorts connector names as plain strings.** i2c.rs:153: `card0-DP-10` sorts before `card0-DP-2`. Cosmetic. **Low.** Fix: natural sort.

**N11. The engine retries writes, and each Linux write already retries 4 times.** i2c.rs:20, 200-214, combined with engine attempts=5 on Transient (tvc-core engine.rs:1059-1060). A NAKed Set VCP 0x60 can be sent up to 20 times, which contradicts the engine's "write input once" intent (engine.rs:796) in the same way as V2. The engine comment says input is written once, but `write()` goes through `run_op` with `attempts`. Worth re-checking in core. **Medium (for 0x60 and action codes).** Fix: a `write_once` path with a single attempt in the backend and in `run_op` for 0x60 and 0x04/0x05/0x08.

**N12. The new code looks correct on these points:**
- `active_targets` handles `ERROR_INSUFFICIENT_BUFFER` with a retry and truncates to the returned `path_count`.
- The `DISPLAYCONFIG_TARGET_DEVICE_NAME` header is set correctly (type, size, adapterId, id), and the `LONG` vs `ERROR_SUCCESS as i32` comparison is right.
- `connector_kind` strips `cardN-` correctly and covers eDP, LVDS, DSI and Virtual.
- `edid::id` format matches the Windows PnP id form (`LEN62A2`).
- The target comparison is case-insensitive on both platforms.
