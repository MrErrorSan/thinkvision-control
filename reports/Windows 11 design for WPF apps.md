# Make ThinkVision Control native, calm and light

**Use WPF's built-in Fluent theme and hand-build the few Windows 11 controls it lacks.** That gives ThinkVision Control a faithful Windows 11 look at no measurable memory cost. WPF-UI looks slightly closer to the Settings app, but measured on this machine it adds about **7 MB of private memory and 160 ms to every launch** (700 ms on a cold launch). Microsoft's Windows 11 design language reduces to five principles: Effortless, Calm, Personal, Familiar, and Complete + Coherent. In practice they mean quiet neutral surfaces, the user's own accent colour used sparingly, 4 px and 8 px rounded corners on a 4 epx grid, Segoe UI Variable text, Mica behind long-lived windows, and stock controls and motion rather than custom ones. For a settings-style utility, Microsoft now documents a specific recipe: a single scrolling column of setting cards, every change applied immediately, settings that don't currently apply disabled rather than hidden with the reason shown, InfoBars for status, and ContentDialogs for destructive actions. That recipe matches what you want for the "monitor not connected" state. **Windows 11 Quick Settings has no third-party extension API, and Microsoft has said so.** Its own DDC/CI tool, PowerToys Power Display, uses a tray flyout and a hotkey instead. Because you let the app exit when the window closes, **its idle footprint is already zero**. The costs you can still affect are launch latency, memory while the window is open, disk size, and (in background mode) the roughly 30 MB one-way cost of showing any WPF window. The single worst setting is single-file compression, which adds 73 MB of private memory for the life of the process.

## Five principles reduce to calm surfaces, stock controls and the user's colours

Microsoft frames Windows 11 as Fluent "evolved… to create a design that is human, universal, and truly feels like Windows". It lists five principles. **Effortless**: "easy to do what I want, with focus and precision". **Calm**: "softer and decluttered; it fades into the background". **Personal**: it "adapts seamlessly to the way I use my device". **Familiar**: "no learning curve". **Complete + Coherent**: a "consistent Windows experience" ([Design principles](https://learn.microsoft.com/en-us/windows/apps/design/design-principles)). Seven signature experiences carry the principles into practice: colour, elevation, iconography, materials, geometry, typography and motion. Microsoft gives no rule-by-rule mapping from principle to practice. Read across those pages, though, the meaning is consistent. Calm means neutral greys, low-opacity fills and 1 px hairline strokes instead of heavy shadows. Personal means following the system theme, accent colour and wallpaper-tinted Mica. Familiar means stock control shapes, the stock type ramp and stock motion, never a private visual language. The Motion page puts it bluntly: "Avoid custom animations where possible… If you can't use WinUI controls, mimic existing OS behaviors" ([Motion](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/motion)).

The foundations are numeric, so fidelity can be checked rather than judged by eye. The table below collects the values a WPF app needs. In WPF, 1 epx (effective pixel) is one device-independent unit.

Voice is part of the language too. Microsoft wants text that is "warm and relaxed", "ready to lend a hand" and "crisp and clear". The user is always "you" and the app is "we", never "I". Buttons and labels take no full stop. Error messages say what happened and what to do next, and they never blame the user ([Writing style](https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style)). Under that rule, "We can't reach your monitor. Check that the cable is connected, then try again." beats "DDC/CI timeout".

Nothing in these foundations changed in substance for 24H2 or 25H2. Most pages keep their 2021–2024 dates with only maintenance edits in 2026. The one addition is a Body Large 18/24 step in the ramp, which suits a large brightness readout. Two documentation quirks are worth knowing. The Typography page both recommends ellipses and later says to clip text instead. The Standard (40×40) versus Compact (32×32) density section disappeared when the Spacing page was merged into "Content layout and spacing" in September 2026 ([Content layout](https://learn.microsoft.com/en-us/windows/apps/design/basics/content-basics)). 25H2-era builds also extend dark mode to legacy dialogs such as File Explorer's copy dialog ([Neowin](https://www.neowin.net/news/windows-11-25h2-finally-gets-long-requested-dark-mode-improvements-and-more-in-new-build/)). An app that still pops a light, unstyled `MessageBox` over a dark UI now looks more out of place than it did in 2021.

Measured against this, the current `PanelWindow.xaml` drifts in small, fixable ways. The page title is 24 px Semibold, which is not a ramp size (Title is 28/36). The slider tick labels are 10 px, below the 12 px minimum. Icons use the deprecated MDL2 font. The connection dot is red versus green with no shape or text difference. App settings use CheckBoxes where a ToggleSwitch is specified. Range controls require an "Apply" click. Confirmations go through `MessageBox.Show`.

## Microsoft now documents a settings-card recipe, down to the margins

The app-settings guidance was rewritten around the Windows Community Toolkit's settings controls. Microsoft asks for "a scrollable layout with a constrained max width (around 1000–1100 px)". Related settings are grouped "under section headers using the **BodyStrong** text style". Each setting is a **SettingsCard**: header, optional description, optional icon, and the control right-aligned on the card. Less-used settings collapse into a **SettingsExpander**, nested no more than one level. An About expander sits at the bottom with the app name, icon and version ([Guidelines for app settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)). The reference XAML fixes the numbers: **4 px between cards**, section headers with margin **1,30,0,6**, max width 1000 ([Toolkit SettingsPageExample](https://raw.githubusercontent.com/CommunityToolkit/Windows/main/components/SettingsControls/samples/SettingsPageExample.xaml)). WinUI Gallery adds a Title-style page header, **36 px side padding** and a 1064 max width ([WinUI Gallery SettingsPage](https://raw.githubusercontent.com/microsoft/WinUI-Gallery/main/WinUIGallery/Pages/SettingsPage.xaml)). On navigation, NavigationView's Top pane suits "5 or fewer" equal categories and the Left pane suits 5–10 or when navigation should be prominent. In Auto mode it shows an expanded left pane at 1008 px and wider, icons only from 641 to 1007 px, and a menu button below that ([NavigationView](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/navigationview)). App settings belong "last… pinned to the bottom" of the pane.

The control-choice rules are equally specific, and they all assume a change takes effect the moment the user makes it. "When a user changes a setting, the app should immediately reflect the change — don't require a confirmation button" ([Guidelines for app settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)). The rules are:

- **ToggleSwitch** for binary settings that take effect at once. A CheckBox is only for "nice to have" items or when a submit step follows ([Toggle switches](https://learn.microsoft.com/en-us/windows/apps/design/controls/toggles)).
- **RadioButtons** for up to five equally weighted options that all need to be visible. A ComboBox when there are more than eight options, when one option is the recommended choice, when the options vary dynamically, or when the choice is "of secondary importance" ([Radio buttons](https://learn.microsoft.com/en-us/windows/apps/design/controls/radio-button), [Combo box](https://learn.microsoft.com/en-us/windows/apps/design/controls/combo-box)).
- **Slider** for "defined, contiguous values (such as volume or brightness)". Give immediate feedback, show the value with its units, use one-word range labels, and "disable all associated labels" when the slider is disabled ([Sliders](https://learn.microsoft.com/en-us/windows/apps/design/controls/slider)).
- **Buttons** for immediate actions and **HyperlinkButtons** for navigation. Button text is usually a single verb ([Buttons](https://learn.microsoft.com/en-us/windows/apps/design/controls/buttons)).

No Microsoft page states a literal "one accent button per view" rule. "Sparingly", together with PowerToys reserving `AccentButtonStyle` for its one primary action, supports treating it as a working rule. It also supports never putting accent colour on a destructive button ([PowerToys GeneralPage.xaml](https://raw.githubusercontent.com/microsoft/PowerToys/main/src/settings-ui/Settings.UI/SettingsXAML/Views/GeneralPage.xaml)).

Three pieces of guidance settle how the app should look when the monitor is missing. First, settings stay visible: "Display the same settings regardless of the app context. If some settings aren't relevant in a certain context, disable the SettingsCard… Use the Description property… to explain why" ([Guidelines for app settings](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/guidelines-for-app-settings)). This is exactly the behaviour you asked for. It overrides the researcher's earlier inference that "not found" should replace the page with an empty state. Second, the app-wide reason goes in an **InfoBar**, which is for a "changed application state". An InfoBar takes up layout space rather than floating over content, and with `IsClosable=false` it stays until the state resolves. Microsoft's own examples are "No Internet" with a "Network Settings" action and "No microphone plugged in" ([InfoBar](https://learn.microsoft.com/en-us/windows/apps/design/controls/infobar)). Severity carries meaning: Error is a problem that has occurred, Warning a possible future problem, Success a completed background task, and Default is information. Icons and colour must not be the only signal. A status-driven InfoBar must not flash in and out, so debounce it. TeachingTips are explicitly ruled out for errors. Third, progress has a vocabulary. An indeterminate **ProgressBar** means "Loading/Working" and does not block. An indeterminate **ProgressRing** means "Connecting…" and does block ([Progress controls](https://learn.microsoft.com/en-us/windows/apps/design/controls/progress-controls)). The older guide treats operations over two seconds as needing feedback and anything under five as needing only an activity indicator ([Progress bars, Win7 UX guide](https://learn.microsoft.com/en-us/windows/win32/uxguide/progress-bars)).

Guarded actions get a **ContentDialog**, never the deprecated message-box style. The title states the issue, the body states the consequence without repeating the title, and the commit button carries a specific verb with "Cancel" as the safe close button on the right ([Dialog controls](https://learn.microsoft.com/en-us/windows/apps/design/controls/dialogs-and-flyouts/dialogs)). WinUI sets no default button. The older confirmation guidance is explicit that a risky confirmation defaults to the safe choice. It also says never to use OK/Cancel and never to write "warning" in the text, and to use "permanently" when an action can't be undone ([Confirmations, Win7 UX guide](https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm)). Routine, reversible changes such as colour mode get no confirmation at all. For hotkeys, PowerToys is the closest Microsoft model. Each shortcut appears as keycaps plus an edit button on a card. Editing opens a dialog that captures keys live. Save is disabled until the combination is valid, and errors and conflicts appear as InfoBars inside the dialog ([PowerToys ShortcutControl](https://raw.githubusercontent.com/microsoft/PowerToys/main/src/settings-ui/Settings.UI/SettingsXAML/Controls/ShortcutControl/ShortcutDialogContentControl.xaml)).

The notification area has no Windows 11-era guidance. The Windows 7 guide, which Microsoft says still applies "in principle", is the reference ([Notification Area UX guide](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-notification)). Its rules: left-click shows "whatever users most likely want to see", ideally a small popup near the icon whose settings take effect immediately. Right-click opens a menu with the default command first and in bold and Exit last. Items that don't apply are removed rather than disabled. The tooltip follows the form "name – status" and does not explain how to use the icon. Status is shown with a single bottom-right overlay. PowerToys adds a theme-adaptive monochrome tray icon as a user option ([PowerToys General settings](https://learn.microsoft.com/en-us/windows/powertoys/general)). The current tray icon is a hard-coded near-white glyph, which disappears on a light taskbar. Its tooltip also explains the Exit-key recovery, which the guide says belongs elsewhere.

## Quick Settings is closed; a tray flyout is the industry answer

**Third-party apps cannot add tiles, toggles or sliders to Windows 11 Quick Settings.** A Microsoft engineer stated in December 2022 that "there is currently no extension API for Windows 11 Quick Settings" ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1124942/api-for-adding-an-item-in-the-windows-11-taskbar-p)). Every Quick Settings change since then has been first-party, most recently Energy Recommendations in a 25 September 2026 Insider build ([Windows Insider Blog](https://blogs.windows.com/windows-insider/2026/09/25/announcing-new-builds-for-25-september-2026/)). The built-in brightness slider cannot be borrowed either. Windows designates "exactly one display panel" for system brightness. Extending that to an external connector is an OEM driver mechanism, needing a custom monitor.inf and graphics-driver support, not a DDC/CI path ([Microsoft Learn: brightness for external connectors](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/supporting-brightness-controls-for-external-display-connectors)). Microsoft Support tells external-monitor owners to "use the buttons on it" ([Microsoft Support](https://support.microsoft.com/en-us/windows/hardware/display-graphics/change-display-brightness-and-color-in-windows)). Windows 10's Action Center never had third-party quick actions either, so nothing was lost ([Wikipedia: Action Center](https://en.wikipedia.org/wiki/Action_Center)).

The strongest evidence is Microsoft's own behaviour. PowerToys Power Display, shipped in April 2026, controls monitors over DDC/CI through a hotkey, a tray icon and a WinUI 3 flyout, and does not touch Quick Settings ([PowerDisplay design doc](https://microsoft.github.io/PowerToys/modules/powerdisplay/design/)). Twinkle Tray and Monitorian follow the same pattern. Twinkle Tray's flyout opens on click and hides when you click away, and it matches the taskbar's theme. Monitorian is itself a WPF app with rounded Windows 11 corners and a `/set` command line ([Twinkle Tray README](https://cdn.jsdelivr.net/gh/xanderfrangos/twinkle-tray@master/README.md), [Monitorian](https://github.com/emoacht/Monitorian)). The surfaces open to an unpackaged WPF app rank as follows.

| Rank | Surface | Needs a resident process? | Fit for this app |
|---|---|---|---|
| 1 | Tray icon → anchored flyout (`Shell_NotifyIconGetRect` + `CalculatePopupWindowPosition`, Desktop Acrylic backdrop) ([Notification area](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area)) | Yes | Best for sliders; same mental model as the volume flyout |
| 2 | Global hotkeys + transient OSD | Yes | Best for repeated steps; already built |
| 3 | **Jump list tasks** (`System.Windows.Shell.JumpList`, in-box WPF, no packaging) ([JumpList](https://learn.microsoft.com/en-us/dotnet/api/system.windows.shell.jumplist)) | **No**: the shell keeps the list | Good for discrete actions (presets, "switch to this PC") |
| 4 | Command-line verbs | No | Scripting, Task Scheduler, Stream Deck |
| 5 | Toasts with buttons via Windows App SDK ([App notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart)) | No (COM-launched) | Event prompts only; adds a runtime dependency |
| 6 | Widgets Board: "only packaged apps can be registered as widget providers" ([Widget provider](https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs)) | No | Poor: MSIX, Adaptive Cards, user must add it |
| — | Quick Settings | — | No API |

The ranking shifts for how you actually use the app. With exit-on-close, ranks 1 and 2 exist only while background mode is on, because both need the process running. **The jump list is the one quick-access surface that works with nothing running.** It appears when the app is pinned to the taskbar or opened from its Start menu entry, which the app already registers. A task such as "Night preset" relaunches the exe with an argument. The existing single-instance path forwards the argument if the app is already running; otherwise the app does the work, shows the OSD and exits. The tray flyout has one hidden cost. It is a WPF window, so its first display pays the same one-way render cost as the main window (next section). It is a UX upgrade, not a resource saving.

## The built-in Fluent theme costs almost nothing; WPF-UI costs 7 MB and 160 ms

.NET 9 added a Fluent theme to WPF, and .NET 10 extended it. Setting `ThemeMode="System"` on the `Application` in XAML restyles the stock controls: Button, CheckBox, ComboBox, RadioButton, Slider, ProgressBar, ScrollViewer, TabControl, ListBox, ContextMenu, Expander, TextBox, ToolTip and more. It follows light/dark and the system accent. On Windows 11 22H2 and later it automatically applies **Mica** (`DWMSBT_MAINWINDOW`) and the dark title bar to each window ([What's new in WPF .NET 9](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net90), [using-fluent.md](https://github.com/dotnet/wpf/blob/main/Documentation/docs/using-fluent.md)). The styles derive from WPF-UI's: the Fluent `Window.xaml` carries the WPF-UI copyright header ([Styles/Window.xaml](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/Themes/PresentationFramework.Fluent/Styles/Window.xaml)). The caveats are real. `ThemeMode` is still `[Experimental("WPF0001")]` in .NET 10 and on the main branch, and Microsoft says Fluent support "is still in progress" ([Application.ThemeMode](https://learn.microsoft.com/en-us/dotnet/api/system.windows.application.thememode?view=windowsdesktop-10.0), [What's new in WPF .NET 10](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net100)). Setting it from XAML triggers no diagnostic; only code access does.

**The theme adds no new controls**: no ToggleSwitch, NavigationView, InfoBar, ContentDialog, ProgressRing, NumberBox or cards. `MessageBox` is still unstyled ([dotnet/wpf#10415](https://github.com/dotnet/wpf/issues/10415)). Open bugs include:

- implicit App.xaml styles overriding Fluent ([#10834](https://github.com/dotnet/wpf/issues/10834))
- animations playing even when Windows animation effects are off ([#11798](https://github.com/dotnet/wpf/issues/11798))
- ComboBox not refreshing when its bound collection changes ([#11844](https://github.com/dotnet/wpf/issues/11844))
- keyboard focus indication weaker than under Aero2 ([#11054](https://github.com/dotnet/wpf/issues/11054))

Once the application-level theme is set, a window cannot opt back out with `ThemeMode=None`. Windows with `AllowsTransparency=True`, such as the OSD, are skipped by the backdrop manager, so Mica never applies to them.

**WPF-UI 4.3.0** (MIT, targets net10.0-windows, released 4 May 2026) is the most complete alternative. It provides FluentWindow with Snap Layouts, NavigationView, CardControl and CardExpander, ToggleSwitch, InfoBar, ContentDialog, NumberBox, a system-theme watcher and selectable Mica/Acrylic/Tabbed backdrops ([NuGet WPF-UI](https://www.nuget.org/packages/WPF-UI), [lepoco/wpfui](https://github.com/lepoco/wpfui)). Against that, it has about 418 open issues, and several releases (3.0.x, 3.1.0, 4.0.x, 4.1.0, 4.2.0) were deprecated on NuGet for "critical bugs". Its tray package has had open bugs since 2022. The other libraries drop out quickly:

- ModernWpf has a promising 1.0 release candidate from September 2026, but it is not yet stable ([ModernWpf rc.1](https://github.com/Kinnara/ModernWpf/releases/tag/v1.0.0-rc.1)).
- iNKORE.UI.WPF.Modern's licence forbids commercial use without permission and requires consumers to be open source ([LICENSE](https://github.com/iNKORE-NET/UI.WPF.Modern/blob/main/LICENSE.md)).
- HandyControl is its own visual language, not Fluent.
- The Community Toolkit's SettingsCard is WinUI-only.

A probe app with this app's shape (a WPF `Application`, a WinForms `NotifyIcon`, and a window of four sliders, a combobox, a checkbox and a button) was measured on this machine under .NET 10.0.12 ([Local measurement](../research_notes/Windows%2011%20design%20for%20WPF%20apps/resource_footprint_data.json)):

| Theme | Before any window (private / WS MB) | Window shown then closed (private / WS MB) | Warm launch to first render | Added disk |
|---|---|---|---|---|
| Aero2 (current) | 12.0 / 42.5 | 41.1 / 89.7 | 613 ms | 0 |
| Built-in Fluent (`ThemeMode` on Application) | 15.6 / 55.3 | 37.5–38.4 / 92–94 | 640–682 ms | 0 (0.98 MB DLL already in the runtime) |
| WPF-UI 4.3.0 | 18.0 / 59.4 | 48.1 / 102.7 | 775 ms (cold 2,125 vs 1,418) | 6.6 MB `Wpf.Ui.dll` |

Two readings matter. Once a window has rendered, Fluent's cost is within noise, and its private memory was actually slightly lower. WPF-UI costs a steady **+7 MB private and +160 ms per launch**. With exit-on-close, every open is a fresh launch, so WPF-UI's startup penalty is paid every time. Second, both themes load at `Application` level, so they raise the never-shown baseline (Fluent +3.5 MB private, WPF-UI +6 MB). That baseline matters only in background mode. Setting `ThemeMode` on each window instead of on the Application should keep it at 12 MB and also leave the OSD unthemed. This is an inference that was not measured.

Mica cost was not measured, but it is designed to be cheap: it "only samples the desktop wallpaper once". Acrylic is "GPU-intensive", which is one more reason to confine it to transient flyouts ([Mica](https://learn.microsoft.com/en-us/windows/apps/design/style/mica), [Acrylic](https://learn.microsoft.com/en-us/windows/apps/design/style/acrylic)).

## A WPF window costs 30 MB once; with exit-on-close, launch time is what you feel

The probe shows where WPF's memory goes. A process that has **never shown a window** idles at about **12 MB private / 43 MB working set** with 12 threads. Showing a window **once** lifts it to about **45 MB private / 92 MB WS** with 25 threads. Closing the window and collecting garbage returns only about 4 MB. Hiding it returns nothing ([Local measurement](../research_notes/Windows%2011%20design%20for%20WPF%20apps/resource_footprint_data.json)). The managed heap is not the cause; it stays at 1.5–2.6 MB. The cost is the native hardware render path, which a WPF contributor also identified in a thread where a blank .NET 8 WPF app used over 90 MB against 6–7 MB for WinForms ([dotnet/wpf#9017](https://github.com/dotnet/wpf/discussions/9017)). `RenderMode.SoftwareOnly` removes about **13 MB private and 7 threads**. It also guards against Intel driver builds that have pushed an empty WPF app to 165 MB ([dotnet/wpf#8306](https://github.com/dotnet/wpf/issues/8306)). Whether Mica still renders under software rendering is untested.

Exit-on-close changes which of these levers matter. Closed, the app costs nothing: no memory, no timers, no I²C traffic. The remaining costs are paid on every launch, so launch latency and disk size become the metrics that matter, plus a bounded 40-odd MB while the window is open. Publish settings dominate both ([Local measurement](../research_notes/Windows%2011%20design%20for%20WPF%20apps/resource_footprint_data.json)):

| Publish variant (win-x64) | Exe size | Warm launch | Private MB after window closed |
|---|---|---|---|
| Framework-dependent single-file | 0.18 MB (needs .NET 10 Desktop Runtime) | 548–658 ms | 38–41 |
| Self-contained single-file + `SatelliteResourceLanguages=en` | 154.7 MB (−18 MB) | 557–729 ms | 42–43 |
| + `EnableCompressionInSingleFile` | 69.3 MB | 701–769 ms | **115** |
| + `PublishReadyToRun` (no compression) | 172.3 MB | **467–491 ms** | 45–46 |

**Compression is a trap for a desktop app.** It shrinks the file but decompresses every assembly into private memory, adding about **73 MB private and 124 MB working set** plus about 100 ms of startup. Microsoft's own docs warn to "measure both the size change and startup cost" ([Single-file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)). **ReadyToRun cuts about 100–140 ms from every launch** for about 17 MB more on disk and 3–4 MB more private memory. Trimming is blocked by the SDK for both WPF and WinForms (NETSDK1175), so NativeAOT is out too ([Trimming incompatibilities](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)). `InvariantGlobalization` saves nothing on Windows. The GC knobs (non-concurrent GC, `ConserveMemory=7`, a 1 MB gen0 budget, `TieredPGO=0`) all measured within noise, because the heap is around 2 MB ([GC config](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector)).

Two more levers apply only in background mode. The 5-second `System.Threading.Timer` reconnect loop wakes the CPU 720 times an hour and probes the I²C bus while the monitor is absent. It also runs while the window is open, so even under exit-on-close it adds up to five seconds of reconnect lag. Replacing it with `RegisterDeviceNotification(GUID_DEVINTERFACE_MONITOR)` or `CM_Register_Notification`, plus display-change and resume events and a short bounded retry burst, makes detection both faster and idle-free ([GUID_DEVINTERFACE_MONITOR](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/guid-devinterface-monitor), [CM_Register_Notification](https://learn.microsoft.com/en-us/windows/win32/api/cfgmgr32/nf-cfgmgr32-cm_register_notification)). Windows 11 also lets a hidden process opt into **EcoQoS**, which runs it at the most efficient CPU frequency and on efficient cores. Microsoft cites "up to a 90% reduction in CPU power consumption" for background work. The app should clear EcoQoS when the window opens, since EcoQoS "should not be used for… foreground user experiences" ([SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation), [Introducing EcoQoS](https://devblogs.microsoft.com/performance-diagnostics/introducing-ecoqos/)). Do not call `EmptyWorkingSet`. It drops the Task Manager figure to 7 MB, but private commit is unchanged and the pages fault back in when used. Lowering memory priority is the documented alternative.

For scale, Twinkle Tray's author reports about 40 MB idle while users report 80–215 MB ([twinkle-tray#879](https://github.com/xanderfrangos/twinkle-tray/issues/879)). The 12 MB never-shown state is well below that, and the opened state is comparable. No published idle figures exist for Monitorian or Power Display.

## Conclusion

Fidelity and lightness point the same way here. Microsoft's own WPF theme carries most of the Windows 11 look for free. The controls it lacks are the four simplest in the settings recipe: a toggle, a card, an InfoBar and a dialog. The heavy items are all deployment and lifecycle choices, not visual ones: single-file compression, showing a window at login, a polling loop, the publish mode. Two changes cross both concerns. Rendering every setting from the bundled monitor profile, instead of waiting for the monitor to answer, delivers the "full UI, disabled, with a reason" state Microsoft prescribes. It also removes DDC round-trips from first paint on every launch. And for someone who lets the app exit, the most useful quick-access addition is not Quick Settings, which cannot be extended, nor a tray flyout, which needs a resident process. It is a jump list, which costs nothing while the app is closed.

## Recommendations for ThinkVision Control

### 1. Implementation approach: built-in Fluent plus four hand-built controls

| Priority | Decision | Reason |
|---|---|---|
| 1 | Set `ThemeMode="System"` in XAML on each themed window (`PanelWindow`, `FinderWindow`, `HotkeyCaptureWindow`), or on `Application` if per-window proves unreliable | Faithful stock controls, Mica, dark title bar and accent for 0 MB extra once shown. Per-window setting should keep the background-mode baseline at 12 MB and leave the OSD unthemed (verify) |
| 2 | Delete or rebase the implicit styles in `Ui/Theme.xaml` with `BasedOn="{StaticResource {x:Type …}}"`. Replace hard-coded brushes with Fluent keys (`TextFillColorPrimaryBrush`, `CardBackgroundFillColorDefaultBrush`, `CardStrokeColorDefaultBrush`, `AccentFillColorDefaultBrush`) via `DynamicResource` | Implicit styles override Fluent ([#10834](https://github.com/dotnet/wpf/issues/10834)) |
| 3 | Hand-build **SettingsCard** (Border, CornerRadius 8, card fill and stroke, header/description/icon, right-aligned content), **ToggleSwitch** (ToggleButton template), **InfoBar** (Border + severity glyph + title + message + action) and an **in-window dialog** (Smoke scrim + 8 px card + Subtitle title + buttons). Use `Expander` for SettingsExpander | These four controls are missing from the theme, and `MessageBox` is unstyled ([#10415](https://github.com/dotnet/wpf/issues/10415)) |
| 4 | Remove the manual `DWMWA_USE_IMMERSIVE_DARK_MODE` call for Fluent-themed windows; keep it only for unthemed ones | WPF sets the attribute itself under Fluent |
| 5 | Switch icon `FontFamily` to `"Segoe Fluent Icons, Segoe MDL2 Assets"` | Same code points; MDL2 is deprecated. Contrast (E7A1) exists only in Fluent Icons |
| 6 | Define local text styles for the ramp (Caption 12/16 through Title 28/36) using Segoe UI Variable | Fluent's coverage of WinUI's named styles in WPF was not verified |
| 7 | Keep the OSD a plain `AllowsTransparency` window with explicit local styles | No backdrop applies to it; keep it independent of the theme |
| 8 | Do not adopt WPF-UI unless a full NavigationView becomes essential; if adopted, pin the version and merge its dictionaries into the window, not `App.xaml` | +7 MB private and +160 ms per launch (+700 ms cold); history of deprecated releases |

Leave the in-app theme picker out at first. Following the system theme is the Personal principle, and setting `ThemeMode` from code needs the `WPF0001` suppression, which exposes you to API churn when .NET 11 ships in November 2026.

### 2. Page and layout structure, and the control for each setting

Use a left navigation pane with **Display** and **Monitor settings** at the top and **App settings** (today's "App & shortcuts") pinned at the bottom, with About as the last expander on that page. That is the Settings and PowerToys pattern, and it puts app settings where Microsoft says they go. A top pane is also valid for three categories if you prefer a narrower window. Open the window at about **1008×720** so the pane starts expanded, and collapse it to icons below that width. On every page, use a Title-style (28/36) header, 36 px side padding, a 1000 px max-width column, BodyStrong section headers with margin `1,30,0,6`, and 4 px between cards. Leave the window background unset so Mica shows behind the cards. Implement F6 to move focus between the pane and the content.

| Page / group | Setting (VCP) | Control | Notes |

| Display / Brightness and contrast | Brightness (0x10), Contrast (0x12) | Card with **Slider** 0–100, step 1, value label with units beside it; Brightness E706 icon | **Remove the Apply button.** Write while dragging (throttled), then on thumb release, then read back. ### 3. States: full UI always visible, controls disabled, reason in one InfoBar

Build the cards from the bundled `p32p20.profile.json` and the last-known capabilities **before** talking to the monitor. Today `Rebuild()` creates no items until capabilities arrive, which is why "not found" shows an empty panel. Monitor-dependent cards are enabled only in the Connected state. App settings and shortcuts stay enabled in every state. While disabled, a slider shows "—" in place of its value, so stale numbers never pass for live ones. Put the reason in a single InfoBar under the page header rather than repeating it on every card. Hold a new state for about a second before swapping the InfoBar so it doesn't flash, and close and reopen the InfoBar so screen readers announce the change.

| State | InfoBar | Progress | Controls | Tray icon / tooltip |
|---|---|---|---|---|
| Connecting | None for the first ~1 s, then Informational: "Looking for your monitor…" | Indeterminate **ProgressBar** (non-blocking) inside the InfoBar | Visible, disabled | Normal icon; "ThinkVision Control – Connecting" |
| Not found | **Informational**, not closable. Title "ThinkVision P32p-20 isn't connected". Message "Connect it and we'll find it automatically." Action **Check again** | None | Visible, disabled | Disconnected overlay at bottom right; "ThinkVision Control – Not connected" |
| Not responding | **Error**, not closable. Title "Your monitor isn't responding". Message "DDC/CI might be off. Hold the monitor's Exit key for 10 seconds, then try again." Action **Try again** | None | Visible, disabled | Error overlay; "ThinkVision Control – Not responding" |
| Connected | None (the values appearing are the feedback) | Thin ProgressBar only while reading settings for more than ~1 s | Enabled. A control the current input doesn't support stays disabled, with "Not available on the HDMI input" in its Description | Normal icon; "ThinkVision Control – P32p-20" |

Not found uses Informational rather than Error because an unplugged monitor is a normal state for a laptop, not a fault. Not responding is a real fault. Replace the red/green dot in the header: the InfoBar and the tray overlay carry state with an icon and text, satisfying the rule that colour must not be the only signal. The tray context menu should drop items that can't run (presets while disconnected) rather than grey them out.

### 4. Quick-access surfaces

| Priority | Surface | Works with exit-on-close? | Scope |

| 2 | **Command-line verbs** (`--set brightness=40`, `--step brightness=+10`, `--preset`, `--input`) | Yes | Shared with the jump list; enables Task Scheduler and Stream Deck |

### 5. Resource-footprint checklist

1. **Keep exit-on-close as the default and background mode opt-in.** Closed costs nothing.
2. **Never enable `EnableCompressionInSingleFile`.** Measured +73 MB private and +100 ms per launch.
3. **Render the UI from the profile and cached values first**, then read the monitor in the background. Removes DDC round-trips from first paint on every launch and enables the disabled-but-visible states.
4. **Built-in Fluent, not WPF-UI.** About 0 MB once shown, against +7 MB and +160 ms per launch.
5. **`PublishReadyToRun`.** −100–140 ms on every launch, which you pay each time you open the app; costs 17 MB of disk.
6. **Either framework-dependent (0.18 MB exe) or self-contained with `SatelliteResourceLanguages=en` (−18 MB).** Memory is the same either way.
7. **Replace the 5 s reconnect timer** with monitor device notifications, display-change and resume events, and a bounded retry burst (0.5, 1, 2, 4, 8 s, then stop). Stop all timers on suspend.
8. **Background mode: launch with `--background` from the Run key and never create a window at login.** 12 MB against 41–45 MB private. Close (don't hide) the window on dismiss, set `MainWindow = null` and unsubscribe from services.
9. **Background mode: EcoQoS (plus low memory priority) while hidden, cleared when the window opens.**
10. **Test `RenderMode.SoftwareOnly`.** −13 MB private and −7 threads, and immune to iGPU driver bloat. Adopt it if Mica and text still render correctly.
11. **Keep motion brief and stock.** Show indeterminate progress only while work is running, and honour the "Animation effects" setting yourself, because Fluent currently ignores it ([#11798](https://github.com/dotnet/wpf/issues/11798)).
12. **Optional: replace the WinForms `NotifyIcon` with a `Shell_NotifyIcon` wrapper.** Drops `System.Windows.Forms.dll` (13.7 MB) from a self-contained bundle. The full saving was not measured.
13. **Don't:** tune GC knobs, set `HeapHardLimit`, call `EmptyWorkingSet`, attempt trimming or NativeAOT, or use a zero-delay logon task.
